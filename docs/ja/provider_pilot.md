# 提供側で管理するH₂契約の限定導入

H₂のEOSと溶解度について、提供側で管理する契約を追加しました。

| 提供側 | 契約 | 監査した実装 |
| --- | --- | --- |
| ExoEOS | `mceg/contracts/zhang_duan_h2.yaml` | mainの`d7681db4393fd85904846b083013230d81d45d4e` |
| ExoGibbs | `mceg/contracts/h2_solubility.yaml` | developの`9990fdc2f4bd8423bdfc0cefdc1fbb8325cfe55f` |

科学モデルの実装と依存関係は維持しています。追加したものは契約、短い説明文、
`results/mceg/`以下の新しい数値テスト実行記録とJUnitファイル、選択したファイルの
ハッシュを確認する標準ライブラリだけのテストです。提供側のテストはMCEGを
インポートしません。構造検査は独立したMCEG環境から任意に実行します。
今回はチェックアウト内のメタデータであり、インストール済みwheelから契約を発見する
仕組みは定義していません。

## 対象と実装の確認

ExoEOSのmainは以前の監査revisionと同じでした。ExoGibbsのdevelopには更新があり、
アダプターに多相計算の関数が追加されていましたが、純成分のcallbackとH₂溶解度関数は
維持されていました。対象ブランチで数値テストを再実行し、ExoEOSの公開パラメーター
読込確認1件と、ExoGibbsの式・broadcast・fugacityと圧力の確認8件が通りました。
後者の記録には、接続テストで使ったExoEOS側の実装も残しています。

古い証拠は元のrevisionに限定した履歴として保存しています。元のMCEG監査文書には
コミット固定URLを使い、契約の移設によってMCEGのチェックアウトへの暗黙の依存が
生まれないようにしました。現在の数値的主張は、別の`provider_test_run`を参照します。
一次資料の確認状況、較正上の注意、物理的な精度の`unknown`は維持しています。

ローカルの証拠パスは、各提供側リポジトリのルートを基準に解決します。
[利用側のスクリプト](../../examples/provider_h2/run.py)は、提供側の数値実行記録も
含め、認識対象のローカルファイルを確認します。外部URL、文章による書誌情報、アンカーは、
[配置試験](provider_trials.md)の限定的な確認処理を使って未確認として報告します。
ファイルの存在と内容の確認は別です。

## 利用側からの再実行

契約を追加した両提供側ブランチと、任意の計算依存パッケージを含む環境を使います。
MCEGのチェックアウトから、次のように実行できます。

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src \
JAX_PLATFORMS=cpu JAX_ENABLE_X64=1 \
python examples/provider_h2/run.py \
  --exoeos /path/to/exoeos \
  --exogibbs /path/to/exogibbs \
  --output /tmp/provider-h2-result.json
```

チェックアウトの場所は明示的に指定し、MCEGと同じ親ディレクトリに置く必要はありません。
実際にインポートしたモジュールの場所も確認します。この例では監査revisionのGitオブジェクトを
読むため、それが含まれない浅いチェックアウトでは再実行できません。

[元のケース](../../examples/h2_solubility/case.yaml)を維持し、1700 K・7500 barと
九つの手動評価を使います。再利用の前に、提供側契約の科学的な記述が元の契約と一致するかを
確認します。記述が変わった場合は、新しい手動評価が必要です。この一致確認は記述や
評価の科学的な正しさを証明するものではありません。出力では各評価の証拠IDを、実際の
提供側契約へ結び付けています。

[保存した実行](../../examples/provider_h2/result.json)には、両契約と実行記録のハッシュ、
監査した実装revision、実際のチェックアウトのrevision、選択したソースのハッシュを記録しています。
四つの数値確認が通り、元のH₂計算と同じphi = 2.2561116480、fugacity = 16920.83736 bar、
溶解モル分率 = 0.1068105175を得ました。九つの手動判定も維持しています。
接続全体の物理的な精度は引き続き不明です。

## 実装のrevisionと契約を公開するコミット

モデルのコードを変えずに契約を追加しても、リポジトリのHEADは変わります。
保存した再実行は提供側のコミット後に行うため、`checkout_revision`と
`audited_revision`は異なります。選択したファイルが、実行記録のハッシュと監査revisionの
Gitオブジェクトの両方に一致する場合に、この状態を受け入れます。記録のハッシュを
書き換えるだけで、新しいコードを古いrevisionの実行結果に結び付けることはできません。

これは選択したファイルの同一性の確認であり、間接的な依存関係や実行環境すべてを確認する
ものではありません。記録した依存パッケージの版と対象範囲も引き続き重要です。
また、ファイルが変わったときに、影響する主張を自動で判断する機能ではありません。
変更があれば再実行を停止してレビューし、新しい監査と実行記録を用意します。
提供側の回帰テストはローカルのハッシュだけを使い、GitやMCEGを必要としません。

元のMCEG契約とH₂の実行記録は、固定した参照例として維持します。
以後のモデル契約は提供側で管理します。利用側の計算ケースとモデル契約は管理者が異なり、
互いの科学的な結論を暗黙に上書きすべきではありません。新しい実行記録の形式と同一性の
確認処理は例専用で、v0.1のスキーマと公開APIは変更していません。
