# 実験的v0.1の設計課題

MCEG v0.1は、実在する科学モデルを小さな契約で正確に記述できるかを
調べる試みです。最終規格でも科学的な承認でもありません。最初の例には
ExoEOSの残差Helmholtzモデル `IdealEOS`、`SecondVirialEOS`、
`PengRobinsonEOS` を選びました。`IdealEOS` は残差エネルギーをゼロとする
モデルであり、理想系の熱量的性質も提供する別クラス `IdealGas` とは異なります。
残差EOSだけでは全体の熱容量、絶対エンタルピー、エントロピーは定まりません。
これらの機能を混同しないことが必要です。

## 設計原則

- MCEGは提供元パッケージから独立させ、ExoEOSやExoGibbsに依存関係を追加しない。
- 科学的な適用可能性と、数値評価のための条件を分ける。
- 数値的なVerificationと、実験・観測に基づくValidationを分ける。
- 主張には証拠とその対象範囲を結び付け、範囲・結果・引用を捏造しない。
- 不明点は `unknown` とし、何が不足しているかを説明する。
- 必要最小限の構造を優先し、データベース・推論エンジン・提供元の実行は後回しにする。
- v0.1は、実例によって不足が明らかになれば変更できる実験的仕様とする。

## 記述しやすいことと難しいこと

実装のシンボル、リビジョン、式、入力の規約、テスト識別子、明示された実装上の
制約は、そのまま記録できます。3例は残差自由エネルギーのインターフェースを共有
しているため、複雑な抽象化は不要です。主張と証拠を識別子で結ぶだけでも、
根拠を追跡するのに役立ちます。

科学的な適用範囲の記述は難しく、式や計算の収束だけでは較正された誤差限界を
得られません。テスト点の間の全領域が検証済みになるわけではなく、任意の係数を
受け取るクラスに、実在物質に対する普遍的な精度範囲はありません。
未知の高次ビリアル係数から、追加の根拠なしに打ち切り誤差の数値基準を
定めることもできません。

## 現在の状態フィールドの意味

実行可能なスキーマは [schema.py](../../src/mceg/schema.py) です。領域の種別は
`scientific_applicability` と `numerical_evaluation`、状態は `documented` と
`unknown` です。`documented` は条件を根拠付きで記録したことを意味し、
提供元が条件をすべて検査することや、実験で適用範囲が確立したことを意味しません。
`unknown` の領域には条件を断定せず、descriptionに不足する情報を説明します。

主張は `theoretical`、`numerical_verification`、`physical_validation` に分け、
状態を `supported` または `unknown` とします。Validatorは、supportedの主張に
対応する証拠種別、すなわち理論、成功した数値テスト・ベンチマーク、または
実験・観測があることを要求します。これは宣言の整合性検査です。
証拠から本当にその主張が導けるか、対象範囲を十分に覆うか、独立した証拠かは
証明しません。

数値的証拠の結果は `passed`、`failed`、`not_run`、`unknown` です。
`not_run` は既知のテストの実行結果がその記録に含まれていないこと、`unknown` は
結果が確立していないことを示します。テストのソースは成功結果そのものでは
ありません。unknownは、偽・安全・適用不可の同義語でもありません。
現在の主張の状態では、証拠の対立や部分的な支持を正確には表せません。

## 実例から明らかになった未解決の課題

1. **何をモデルの識別単位にするか。** クラス、係数集合、成分順序、混合則、
   根の選択、ソフトウェアのリビジョンは、それぞれモデルの意味を変えます。
   v0.1は実装を識別しますが、型付きのパラメーター集合の識別や、一般モデルと
   具体的な設定の継承関係は持ちません。
2. **領域をどう実行可能にするか。** `conditions` は説明文であり、判定式では
   ありません。Second Virialの判別式が正という条件と低密度近似は別の意味を
   持ちます。PRでも根の存在、根の滑らかさ、実験に対する精度は異なります。
   将来の条件言語には、単位、組成、条件付き領域、厳密な境界、不明という結果が
   必要です。v0.1は計算状況を評価せず、外挿箇所を自動判定しません。
3. **単位と規約をどう組み合わせるか。** ExoEOSはPaとモル密度を使い、
   ExoGibbsのアダプターは圧力をbarで受け取り、無次元係数の自然対数を返します。
   次元が合うだけでは、質量・モル基準、対数の底、残差・全エネルギー、基準圧力を
   区別できません。v0.1はこれらを文章に記録し、自動変換や比較は行いません。
4. **化学種と標準状態をどう対応させるか。** 配列順序だけでは、各係数が宣言した
   物質に属することを保証できません。溶液の活量係数には対応する標準化学
   ポテンシャルも必要で、活量規約のラベル一致だけでは不十分です。
   整合的な標準状態の変更には、標準ポテンシャルと活量双方の補償が必要になり得ます。
5. **証拠はどこまでを支持するか。** 解析的恒等式は仮定の下で成立し、人工的な
   テストや有限のグリッドは指定した数値ケースを検証します。別実装との一致は
   測定ではありません。文献はモデルを説明していても、手元の実装や新たな
   パラメーター集合の精度を確立するとは限りません。実験・観測による支持には、
   実際のデータ、条件、ずれの判定基準が必要であり、引用やpassedから推測しません。
6. **結果の再現性をどう維持するか。** リビジョンを固定した出典は有用ですが、
   dtype、バックエンド、依存関係、テスト選択、パラメーター、実行記録も結果に
   影響します。v0.1はsourceとscopeの文字列を持ち、構造化した実行記録や成果物の
   ハッシュは持ちません。Validatorはテスト実行、出典の取得・存在確認、記録済み
   結果が現在も有効であることの認証を行いません。
7. **失敗や不確かさをどう伝えるか。** 液相・気相の根を選ぶことは、大域的な
   相安定性の証明ではありません。小さな残差や微分の成功も物理的な誤差を
   定量化しません。v0.1には不確かさの伝播、証拠の独立性、主張の対立の解決、
   契約間の自動整合性検査がありません。証拠の不足を暗黙の保証に変えず、
   見える状態に保つ必要があります。

## 初期の3契約から接続例へ

最初の接続例は、以下の純成分アダプターを使う
[H₂溶解度のケース](h2_solubility.md)として追加しました。
手動判定の形式は実験用であり、コアスキーマの拡張ではありません。

[この例で使うExoGibbsの純成分アダプター][adapter] は、barからPaへの
変換、化学種順序の保持、欠落種に対する明示的な方針を含みます。
mockを用いたテストは接続の動作を検証し、物理的な精度は検証しません。
ギャラリーの例では標準化学ポテンシャルをゼロにしているため、その実行圧力を
実在する化学組成の適用範囲とはみなせません。

[M2の混合物providerとの接続][mixture] は、より多くの課題を含む候補です。
Second Virialのペア係数に、外挿または `hold_2000` の方針を明示し、モデル化
されていないペアの係数をゼロとします。ペア係数がゼロの微量種にも混合物全体の
補正が働き、独立した理想種の補正にはなりません。反復計算の許容誤差は測定の
不確かさではありません。したがって、公開されている純成分アダプターの制限を
ExoGibbsの全例に一般化できません。混合物の契約は今回のPoCの対象外です。

一般的なルールエンジンを設計する前に、さらに具体的な計算設定を増やし、
パラメーターの出典と証拠の不足も含めて記述するのが有用です。
[残差APIの説明][residual] と [標準状態の対応例][standards] は、その設計を
評価する具体例になります。

## H₂の接続で明らかになった課題

1700 K・7500 barに固定した計算は有限の数値を返しましたが、EOSの入力は
報告された純H₂のPVT比較データ範囲を超えていました。溶解度則の温度と総圧は
記録区間に入り、実際のメルト組成と実験のフガシティ範囲は不明のままでした。
[手動ケース記録](../../examples/h2_solubility/case.yaml)では、全体に一つの
適用可否フラグを付けず、これらを別々に記録しています。

- **境界は何の範囲か。** EOSの境界は体積比較の証拠範囲であり、フガシティ誤差の
  実測範囲ではありません。各軸の範囲を満たしても、条件全体の適用域は定まりません。
  将来の境界表現には、評価量、証拠の種類、出典、範囲の意味を結び付ける必要があります。
- **どの出典が適用条件を定めるか。** ExoGibbsのメタデータは1673–1773 K、
  玄武岩質メルト向けの式の出典は1673–1723 Kです。今回の温度は両者に含まれるため、
  温度の分類は変わりません。それでも、出典ごとの領域を一つの確定範囲に
  黙って置き換えることはできません。
- **引数にない条件をどう扱うか。** 溶解度関数はフガシティと総圧だけを受け取ります。
  温度や玄武岩質メルトという科学的条件は残ります。APIの引数だけでは契約を
  完全には記述できず、未指定の組成を適合と判定することもできません。
- **更新された証拠をどう表現するか。** 2025年の再較正は、維持されている旧式の
  濃度スケールに問題を提起しています。現在の主張状態では、対象を限定した異論や
  旧証拠の更新を表せません。この知見だけで今回の結果を10分の1にする根拠にもなりません。
- **計算そのものをどこに記述するか。** 個々のモデルは既存契約に収まりますが、
  接続、具体的入力、手動判定、実行記録には別の記述が必要です。今回は汎用の
  ワークフローグラフを設計せず、参照とハッシュで結んだYAML・JSONに分けました。

次に有用なのは、出典と対象を明示した小さな境界レコードと、未知の入力の表現です。
自動推論や全体の整合性判定は、手作業で監査した計算例を増やし、必要な意味づけが
明らかになってから検討するのがよいと考えます。

## 一次資料まで戻る仕組み

任意の[出典追跡レコード](provenance.md)に、対象を限定した一次資料、確認状況、
引用経路での手動照合を記録できるようにしました。H₂の温度範囲では、確認済みの
二次資料の記述と、未確認の元の実験表を分けています。構造検査と追跡レポートは
この不足を示し、二次資料の正誤は断定しません。

変換や意図した近似の記述、単位や物質ごとの適用域の比較、出典や解釈が更新された
場合に過去の照合を無効化する方法は残された課題です。確認状況は記録された対象に
ついての状態であり、論文全体には一般化できません。要旨の確認は実験表の確認を
意味せず、出典同士の一致は物理的Validationではありません。一次資料にも誤りや、
後に改訂された較正への依存があり得ます。

同一IDの共通引用元は追跡できますが、別IDが同じ実験を表すかは解決していません。
引用数を独立した証拠の数として使うことはできません。全文の取得と正確な情報抽出は
別の作業であり、DOIを追加するだけでは監査は完了しません。こうした科学的な区別の
多くは、まだ実行可能な規則ではなく、scopeなどの説明文が担っています。

## 一次資料監査を試みて分かったこと

[H₂の監査](h2_primary_audit.md)では、原著要旨には到達しましたが、元の実験表と
フィットは取得できませんでした。後年の校正研究の本文も確認しました。
既存の項目だけでこの部分的な結果を記録でき、物理的な主張を変更する必要は
ありませんでした。同時に、次の四つの限界が具体的になりました。

- **取得と確認は別。** DOIが有効、書誌情報のダウンロードが成功、公開資料という
  検索結果がある、というだけでは該当箇所を読んだことになりません。
  v0.1では取得失敗を説明文に記録しますが、取得記録や資料の版を表す専用構造はありません。
- **照合対象を限定する必要がある。** 研究全体の圧力上下限が一致しても、物質ごとの
  適用可能性は引き継げません。温度上限の違いも、転記ミスではなく対象実験の違いかも
  しれません。数値の一致、対象の一致、違いの説明を、現在は一つの状態と文章で扱っています。
- **一次資料も他の情報に依存する。** 濃度測定は以前の赤外吸収係数に依存し得ます。
  新しい係数にも、測定したガラスから別組成への移用があります。`derived_from`だけでは、
  引用、校正、単位変換、フィット、物質間の移用を区別できず、説明文が必要です。
  将来は信号・校正係数・換算濃度を区別したい一方、全装置の依存関係を無制限に
  記録する仕組みにはしたくありません。
- **読んだことと再現したことは別。** 新しい回帰結果を読むことは再フィットではなく、
  再解析を読むことは元データの独立な照合ではありません。対象を限定した記述が
  `inspected`でも、これらの別作業は未実施であり得ます。追跡の完了フラグにも
  この限定された意味を保つ必要があります。

今回は転記ミスの確定や経験式の係数の訂正には至っていません。
資料間の未解決の違いや監査の未完了も、有用な結果として機械可読データに残すべきです。
