# 固定したv0.1を使った導入前の試験

今回の三つの試験は、別種のモデル接続、提供側リポジトリへの契約配置、実装変更時の
更新を実際に試すものです。v0.1のスキーマ・公開API・依存関係は変更せず、ExoEOSと
ExoGibbsにも変更を加えていません。

モデル契約は既存のMCEG形式を使います。一方、計算ケース、実行記録、移設試験の
報告は例専用の形式です。適用可能性の自動判定や、一般的な参照解決仕様、証拠の
自動失効機能を新設したわけではありません。

## 1. 混合気体の接続と、明示的な近似方針

[ケース](../../examples/virial_mixture/case.yaml)では、実在するExoGibbsの
`m2_gas_eos.build_gas_eos`と`with_gas_residual`を使い、ExoEOSの混合気体用
Second Virialモデルを理想気体のGibbsエネルギーに接続しました。以前のH₂溶解度で
使った純成分向けの公開アダプターとは別の接続です。

温度は1500 Kと2173.15 K、圧力は270 barです。成分を
`[H2, He1, H2O1, O2, Mg1]`の順に並べ、物質量を
`[0.75, 0.17, 0.06, 0.012, 0.008]` molとしました。組成は上流のテストで使われている
人工的な例です。標準化学ポテンシャルはすべてゼロ、標準圧力は1 barと明示しています。
したがって、これは固定組成での接続確認であり、化学平衡や惑星大気の存在量の計算では
ありません。H₂–Heの係数10 cm³/molは感度を見るための仮定値です。
O₂またはMgを含むペアの係数はすべてゼロとしています。

[提供側の契約](../../examples/virial_mixture/provider.yaml)と
[接続側の契約](../../examples/virial_mixture/adapter.yaml)を分け、係数の科学的な
仮定と、アダプターの数値的な責任を記録しました。両者が参照する実行記録は同じ一回の
記録です。二つの契約から引用しても、独立した証拠が二つ得られたことにはなりません。

### 数値結果

[保存した実行記録](../../examples/virial_mixture/result.json)では、CPU・倍精度で
35項目の確認が通りました。密度・圧力とVirial式の比較、Gibbsエネルギーと化学
ポテンシャルの比較、独立に自動微分した物質量微分との一致、係数の固定・外挿方針を
確認しています。

| 温度（K） | 水を含む交差係数の方針 | Z | O₂とMgそれぞれのln(phi) |
| --- | --- | ---: | ---: |
| 1500 | extrapolate | 1.0271722732 | -0.0268096610 |
| 1500 | hold_2000 | 1.0271722732 | -0.0268096610 |
| 2173.15 | extrapolate | 1.0179722652 | -0.0178126733 |
| 2173.15 | hold_2000 | 1.0179837779 | -0.0178239828 |

温度・圧力を固定すると、`ln(phi_i) = 2 rho (B x)_i - ln(Z)`です。
その成分の係数行をすべてゼロにしても、`-ln(Z)`が残ります。
微量成分を物質量の分母から除いたり、その補正をゼロとしたりすると、宣言した
Gibbsエネルギーとは違うモデルになってしまいます。

### 手作業による適用範囲の整理

| 確認対象 | 判定 | 判定の意味 |
| --- | --- | --- |
| 提供実装の1000–3000 K | 記録された範囲内 | 数値評価の条件に限る |
| 1500 Kでの水を含む交差係数 | 記録された範囲内 | H₂–H₂Oは200–2000 K、He–H₂Oは100–2000 K |
| 2173.15 K、extrapolate | 外挿 | 記録された温度上限より先に相関式を延長 |
| 2173.15 K、hold_2000 | 外挿 | 境界での係数を、それより高い物理温度で使用 |
| He–Heの表の部分集合 | 記録された範囲内 | 理論値の表の温度範囲であり、補間誤差の上限は別問題 |
| 純成分係数、仮定したH₂–He係数、ゼロとしたペア、高次Virial項の物理誤差 | 不明 | 新しい実験的な誤差評価はない |
| 接続全体の化学ポテンシャルの精度 | 不明 | 数値的一貫性は物理的Validationではない |

`hold_2000`が固定するのはH₂–H₂OとHe–H₂Oの二つの交差係数だけです。
気体そのものの温度は2173.15 Kのままで、実験的な支持範囲が広がるわけではありません。
高次Virial項の欠落も解消しません。二つの計算結果が近いことは、この二つの近似の差が
小さいという情報であり、真値を挟む誤差幅や、近似の正確さを示すものではありません。

ここで用いた出典別の温度範囲は、上流の`gas_virial_sources.json`を確認して記録した
ものです。この台帳には原著の識別子・PDFハッシュ・確認記録がありますが、今回MCEG側で
原著PDFを再取得して照合したわけではありません。そのため台帳を二次的な証拠として扱い、
一次資料への追跡は未完了のままにしています。[H₂の一次資料監査](h2_primary_audit.md)で
学んだ「台帳を読んだことと原著を読んだことを分ける」という原則を適用しています。

### 再実行

ExoEOSの`d7681db4393fd85904846b083013230d81d45d4e`、ExoGibbsの
`6b4cef45d2a6f1eb1462afd6cb6d3f1c77dba8ea`を使います。追跡対象ファイルに変更が
ある場合は停止します。また、ケースの入力変更は、任意依存パッケージを読み込む前に
検出し、新しい手動監査を要求します。

```bash
PYTHONDONTWRITEBYTECODE=1 \
PYTHONPATH=src:../exoeos/src:../exogibbs/src \
JAX_PLATFORMS=cpu JAX_ENABLE_X64=1 \
python examples/virial_mixture/run.py --output /tmp/mceg-virial-result.json
```

JAX、NumPy、SciPy、提供側チェックアウトは、この再実行だけの任意依存です。
実行記録には版、実装revision、選択したファイル、入力、実行コード、契約のハッシュを
保存します。環境全体の完全な保存ではありません。既存の上流テストは読みましたが、
今回の新規契約では`not_run`と記録しています。今回実際に実行した数値的証拠は、上記の
35項目を確認する接続計算です。

## 2. 提供側リポジトリへの配置

[試験スクリプト](../../examples/provider_workflow/run.py)は提供側の固定revisionの
Gitオブジェクトを読み、新しい出力ディレクトリに必要なファイルの部分コピーを作ります。
既存の五つの契約を次のように配置します。

```text
providers/exoeos/mceg/contracts/       # four EOS contracts
providers/exogibbs/mceg/contracts/     # one solubility contract
providers/<owner>/mceg/evidence/       # copied MCEG audit documents
```

実装とテストは、各提供側ルートから見た元のパスを維持します。同じ提供側を指すGitHubの
ソースURLをリポジトリ相対のパスに変換し、MCEGの監査文書は
`mceg/evidence/docs/en/...`へコピーします。参照確認にはリポジトリのルートを明示的に
渡すので、作業ディレクトリやYAMLの配置場所に依存しません。

[保存した報告](../../examples/provider_workflow/result.json)では、次の二つを確認しました。

1. H₂の契約だけをコピーすると、構造検査は通りますが、移設先には
   `docs/en/h2_solubility.md#verification`がなく、参照が切れます。
2. パスを整理して監査文書をコピーすると、五つの契約すべてが構造検査に通り、認識対象の
   ローカル証拠ファイルも存在します。元と移設後の契約、参照ファイルのハッシュを保存しました。

この小さな確認処理が認識するのは、既存契約の`src/`、`tests/`、`documents/`、`docs/`、
`examples/`、`mceg/`で始まるファイル参照です。`sources`には普通の文章による書誌情報も
あるため、それは未確認のまま別に報告します。外部URL、行番号やMarkdown見出しのアンカー、
Pythonのシンボル、コピーしたMarkdown本文内のリンクも未確認です。ファイルが存在することは、
引用が正しいことや該当箇所を読んだことを意味しません。生成物はインストール可能な
提供パッケージでも、完全なオフライン資料集でもありません。

MCEGのルートから、まだ存在しない出力先を指定して実行できます。

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src \
python examples/provider_workflow/run.py --output-dir /tmp/mceg-provider-trial
```

別のチェックアウトには`--exoeos`と`--exogibbs`を指定します。保存済みの試験は、
作業ディレクトリを`/tmp`にし、スクリプトとインポートのパスを絶対指定して実行しました。
必要なのはGitとMCEGだけで、提供パッケージやJAXをインポートしません。
提供側チェックアウトは読み取り専用で使い、生成物は出力先に置きます。

## 3. 実装変更時に過去のpassedを引き継がない

同じスクリプトが別の`candidate/`コピーを作り、H₂の式を
`exp(-11.403 - 0.76 * P)`から`exp(-11.303 - 0.76 * P)`へ変更します。
これは更新手順を試すための意図的・人工的な変更です。転記ミスを発見したわけでも、
係数を訂正したわけでも、提供側の新しい版を作ったわけでもありません。
変更後のモデル計算も実行していません。

候補のrevisionは`synthetic-sha256:<source digest>`とし、実在のGitコミットと
区別します。元の契約と実装はバイト単位で保持し、変更した証拠ファイルと変更前後の
ハッシュを報告に記録しました。

比較のため、元の契約のrevisionだけを書き換える操作も試しました。構造検査は通り、
古い数値的主張は`supported`のまま残ります。v0.1が証拠の鮮度を確認しないことを
実際に示す結果です。一方、[候補の契約テンプレート](../../examples/provider_workflow/candidate.yaml)
では、次のように手作業でレビューした状態を記録しました。

| 記録 | 変更前 | 変更後 | 理由 |
| --- | --- | --- | --- |
| 圧力固定時の線形性 | supported | supported | fugacityに比例する代数形は変わらない |
| 数値的な式の確認 | supported / passed | unknown / not_run | 古い実行は新しい実装を検査していない |
| 過去の数値的証拠 | passed | 元revisionに限定したpassed | 過去に通った事実そのものは消さない |
| Seo Eq. 6との式の照合 | consistent | discrepancy | 意図的に変えた定数が、以前確認した式と異なる |
| 物理的な精度 | unknown | unknown | 新たな実験的検証はない |
| 較正に基づく適用領域 | 元の出典別記録 | 候補についてはunknown | 任意に変えた式へ元の較正範囲を自動で移せない |

この候補は手動レビューの記録であり、影響する主張を自動抽出した結果ではありません。
過去の`passed`を、候補の数値的主張を支える証拠には接続していません。
候補の出典追跡では意図的な不一致が見えますが、新しい科学的発見とは扱いません。
元の契約とソースは`providers/exogibbs/`に残ります。

実際の更新では、旧実行記録を保存し、実装・係数の差分を確認し、影響する主張・出典との
照合・適用範囲をレビューしてから、必要なテストを実行し、新しい記録を保存します。
実行して失敗した場合は`failed`であり、`not_run`は未実行の場合です。単にテストを通すために
期待値を書き換えてはいけません。

## 提供側への導入について分かったこと

これらの違いは、v0.1に項目を追加せずに記録できました。一方、参照の基準ルート、
変更されない監査記録の保存、係数・方針を含むモデルの識別、更新後のレビューについては、
運用上の取り決めが必要です。契約を書いたコミットと、監査した実装のrevisionも別です。
契約を追加するコミット自身のハッシュをその契約に埋めようとすると、循環してしまいます。

今後は、各パッケージ一つ程度の契約から限定導入し、参照・更新の取り決めを確かめる段階に
進めます。そのためにスキーマを広げる必要はありません。一般的な参照解決、変更の影響を
受ける主張の自動発見、パッケージ間の科学的な適用判断は、引き続き未実装です。

確認結果は、**MCEGの68テスト成功**、八つの契約・テンプレートの構造検査成功、混合気体の
**35項目の数値確認成功**、別配置と変更手順の試験完了です。MCEGのテストには提供パッケージも
JAXも不要です。元の五契約、H₂の例、固定したコアは変更していません。
混合気体の物理的なValidationは引き続き不明です。
